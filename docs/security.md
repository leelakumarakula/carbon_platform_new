# Security

| Control (spec §30) | Implementation |
|---|---|
| Password hashing | bcrypt (cost 12); policy ≥12 chars, letters + digits, ≤72 bytes, no edge spaces |
| Access token | HS256 JWT, 15 min, `sub`/`sid`/`iss`/`exp`/`jti`, kept in memory by the SPA |
| Refresh token | 48 random bytes; only its SHA-256 is stored; httpOnly + SameSite=Strict cookie on `/api/v1/auth`; rotated on every use; reuse revokes the session and logs a CRITICAL event |
| Session control | Every request checks the session isn't revoked or expired and the user is ACTIVE (a SUSPENDED or DEACTIVATED account is cut off at once). The sign-in lockout is deliberately **not** checked here: it blocks new sign-ins only, so nobody can sign a user out by typing wrong passwords for their email |
| Lockout | 5 failures → 15-minute lock on new sign-ins (configurable), counted with one atomic database increment (parallel guesses cannot overwrite each other); wrong current passwords on password change count too, the session that reaches the threshold is ended, and no current password is checked while the account is locked (`ACCOUNT_LOCKED`); generic sign-in error message; login audit records the real reason. Database-backed, so it works while Redis is down |
| Rate limiting | Fixed one-minute windows behind one abstraction (`app/core/rate_limit.py`, Phase 12B D18–D21): sign-in per IP and per IP+email (10), refresh per IP (100), every API request per IP (600), per user (1,000), per organization (5,000), uploads per user (100) and a deployment-wide burst ceiling (10,000). Backend `memory` (one process: development, tests) or `redis` (shared, hashed keys, counters only); **production requires `redis`**. A Redis outage fails open (D20), logged and visible in metrics and readiness. A sign-in flood is audited once per client IP per window (one security event + login-audit row), not once per refused request |
| Authorization | permission check per route + organization scoping in services; escalation guards; last-admin protection; account management needs scope over all of the target's organizations and every privileged permission the target holds (no takeover of platform or security accounts); platform-wide grants stay inside the caller's environment (DEMO / LIVE); grants of suspended or archived organizations are ignored |
| Temporary passwords | `must_change_password` blocks every permissioned endpoint until changed |
| Input validation | Pydantic schemas; e-mail normalisation; codes upper-cased and pattern-checked |
| Headers | nosniff, frame DENY, no-referrer, Permissions-Policy, API `Cache-Control: no-store` and CSP `default-src 'none'`, HSTS in production; the SPA is served by nginx with its own CSP (`script-src 'self'`, map tile origins allow-listed) and user text is never rendered as HTML in map tooltips |
| CORS | explicit origin list; credentials allowed only for those origins; allowed request headers `Authorization`, `Content-Type`, `X-Request-ID`, `Idempotency-Key` |
| Client IP and request id | the TCP peer, unless it is in `TRUSTED_PROXIES` — then the right-most untrusted `X-Forwarded-For` hop (uvicorn runs with `--no-proxy-headers`). An incoming `X-Request-ID` is adopted only from a trusted proxy (and only if well formed); otherwise the API generates one, so clients cannot plant ids in audit rows |
| Errors | one envelope `{success:false, error_code, message, details, request_id}`; an unhandled error becomes `500 INTERNAL_ERROR` inside the request middleware, so it still carries `X-Request-ID`, CORS and security headers and is written to the access log; SQL text and tracebacks are never returned |
| Body size | 25 MB request limit (`MAX_REQUEST_BYTES`) enforced on the bytes actually received, so chunked / undeclared bodies are cut off too (413); a larger declared Content-Length is refused before reading; uploads read with a bounded reader, max `MAX_UPLOAD_BYTES` (15 MB) |
| File uploads | type sniffed from content, not the extension or the client MIME type (PDF/PNG/JPEG/WebP, GeoJSON/KML); filenames sanitised; SHA-256 checksum; antivirus boundary (Phase 12B-I): no vendor is selected yet (D13), so production refuses to start without a registered real scanner; the development `signature` scanner records NOT_SCANNED (never CLEAN) and documents are quarantined until a clean rescan; files served only through the API as attachments; versions append-only |
| KML/XML | DOCTYPE/ENTITY declarations rejected (no XXE or entity expansion); vertex limit 5000 |
| Personal data | KYC ID numbers: only a keyed HMAC fingerprint and the last 4 digits are stored. Bank account numbers: Fernet-encrypted (`DATA_ENCRYPTION_KEY`), only the last 4 digits returned. KYC and bank-proof documents are RESTRICTED |
| Record access | organization scope **or** self-service via `farmers.self` + a linked login; out-of-scope records 404; cross-org overlap details hidden |
| Projects | organization-scoped access (404 outside scope); project roles never grant permissions (the user must hold the role); eligibility approver ≠ submitter; carbon-rights reviewer ≠ recorder; buyers and farmers have no project-wide view (farmers: own participation only); other organizations' overlapping projects shown without identity |
| Methodologies | versions approved by a second person; approved versions immutable (new version to change); rules engine only proposes; confirmation needs a specialist recommendation by someone else; locked methodology changes only via audited unlock; evaluations, results and change history append-only |
| MRV / sampling | MRV only on a LOCKED methodology version; plan, stratum, design, relocation, field-record, QA and dataset approvals by a second person; field collectors see and change only their own assigned points/collections and approve nothing; CONFIGURATION_REQUIRED gaps need an audited acknowledgement; approved plans, strata and datasets are never edited (new versions); dataset snapshots hashed (SHA-256) and re-verified on approval; buyers, labs, VVB, finance and farmers have no MRV access |
| Laboratory | two-sided engagements (proposer ≠ accepter); laboratory-facing API returns explicit allow-list schemas only (no farmer / farm / GPS / MRV data) and only for samples shipped to that laboratory; laboratory documents PDF only; custody events and QA reviews append-only and approved results immutable (DB triggers); one APPROVED result per root sample + rule; lab QA separation of duties (analyst, submitter, registrant, sealer, shipment creator / dispatcher, retest requester); report SHA-256 re-verified at QA; DEMO and live never mixed |
| Calculation | only registered methodology modules execute (13 are registered, all NOT_PRODUCTION_READY); NOT_PRODUCTION_READY modules blocked in production; inputs frozen with SHA-256 and re-checked before execution; outputs hashed and re-verified at approval; no request carries a value; runs, inputs, outputs and completed QA protected by DB triggers (never edited or deleted); QA / approval never by the run's creator, freezer, executor or submitter; organization-scoped (404) |
| Internal pre-verification | findings: identity / target / text immutable, append-only history, targets confined to the run, resolver ≠ responder, withdraw by raiser; reports: built from frozen data only, deterministic PDF, content + PDF SHA-256, tamper detection on verify and download, immutable; readiness: independent approval, frozen manifest hash, automatic invalidation; DB triggers; no VVB access |
| VVB / ACVA verification | separate allow-list API (`/vvb`) scoped per assignment: user in the VVB organization, `org_type` VVB, ACTIVE, same environment, accepted assignment, matching project / period / submission, allow-listed resource — otherwise 404; package view without farmer names, contacts, KYC, bank, agreements or audit; downloads only of manifest-referenced or submission-attached documents (KYC / bank / agreement / consent / land / RESTRICTED excluded), integrity re-hash, audited in both organizations; COI declaration required and fixed; decider ≠ finding raiser; submissions, decisions and events protected by DB triggers; the platform records the VVB decision and never verifies, validates or issues |
| Registry & issuance | registries are external counterparties (no portal, no registry users); all records organization-scoped (404 outside); every manual record needs the registry reference and a PDF; frozen snapshot + SHA-256, idempotency key and external references fixed by triggers; issuances confirmed by a second person (DB check confirmer ≠ recorder); issued ≤ VVB-stated only with explicit unit equivalence, never converted; serials stored verbatim, never generated, unique per registry; registry documents immutable; registry events append-only; no inventory, transfer or retirement |
| Credit ledger | UTXO positions and append-only entries protected by DB triggers (conservation on posting, consume-once, RETIRED terminal, no delete, final workflow states immutable); locked reads (UPDLOCK, HOLDLOCK, ROWLOCK) + guarded single-row consumption in one transaction — the loser of a race gets 409 INSUFFICIENT_AVAILABLE and a CREDIT_DOUBLE_SPEND_CONFLICT audit; balances derived, never accepted from a client (strict schemas); dual control on opening, completion, retirement and reversal (DB check confirmer ≠ requester) by a credits.confirm holder of the custodian organization; REGISTRY transfers and retirements only with the registry reference + PDF evidence (immutable documents); holder view allow-listed (no farmer, farm, location, KYC, bank, agreement, audit or other-holder data); Idempotency-Key on every POST; 9A correction / cancellation blocked after ledger activity; DEMO has no credits; no price, order or payment |
| Marketplace | authenticated only; allow-listed listing disclosure (SHA-256) — no farmer, farm, location, KYC, bank, MRV, laboratory, VVB-internal or calculation-internal data; buyer / seller isolation of orders, payments and refunds (404); restricted, PDF-only buyer KYC documents visible to the buyer and the platform reviewer only; KYC gate on ordering, paying and receiving; the 9B ledger stays the only ownership / availability record (no stored balance); every movement through the composable 9B functions under one transaction with the lock order listing → order → payment → reservation → positions; Idempotency-Key on every POST; append-only, deduplicated payment events; no public webhook and no mock payment provider (MANUAL only); dual control on KYC, listing approval, payment confirmation, refunds and delivery; refunds never move credits and a completed REGISTRY transfer is never reversed; DEMO holds no listing, order or payment |
| Separation of duties | KYC submitter ≠ verifier, bank account adder ≠ verifier, farm submitter ≠ verifier, evidence capturer ≠ reviewer |
| Audit | append-only tables enforced by DB triggers; secrets never logged (`SENSITIVE_FIELDS`) |
| Secrets | `.env` in development (never committed); production reads secrets only from the secret-store mount (`SECRETS_DIR`), never from `.env` or environment variables, and requires secure cookies and distinct keys. Data-key rotation: MultiFernet with `DATA_ENCRYPTION_PREVIOUS_KEYS`, then `python manage.py rotate-data-key [--dry-run]` re-encrypts stored bank account numbers; JWT signing keys rotate by `kid` (`JWT_PREVIOUS_KEYS`). Losing the data key makes stored bank numbers unrecoverable, so keep it in the secret store with a backup |
| MFA | columns and a secret-store reference are ready; enrolment flow planned with Security Admin tooling |

Tests in `backend/tests` cover: unauthorized access, role escalation, cross-organization access, invalid,
expired and forged tokens, refresh-token reuse, lockout, rate limiting, and append-only enforcement. Phase 2 adds: cross-organization farmer/farm access, self-service limits, restricted documents, separation of duties, file-type spoofing, the EICAR test file, unsafe KML, and the absence of clear-text identity and bank numbers in responses and the database. Phase 5 adds: MRV RBAC per role, organization isolation of MRV records, collector restrictions (own points only, no review), separation of duties on every MRV approval, and snapshot-hash lineage. Phase 6 adds: laboratory allow-lists and organization isolation, two-sided engagements, laboratory QA separation of duties, the append-only / immutability triggers, PDF-only laboratory documents, and the wind-down rules after an engagement ends. Phase 7 adds: calculation RBAC and isolation, refusal of value-carrying requests, separation of duties on calculation QA / approval, production blocking of NOT_PRODUCTION_READY modules, input / output hash verification and the calculation triggers. Phase 8A adds: finding targets and separation of duties, report determinism and tamper detection, readiness blockers / approval separation / invalidation, Phase 8A triggers and isolation (incl. VVB). Phase 9B adds: real double-spend races on separate database connections (reservations, transfers, retirements, reservation vs retirement), fault-injected rollback, the ledger triggers (append-only, conservation, consume-once, RETIRED terminal), ledger RBAC and separation of duties, the holder allow-list, and the 9A correction guard. Phase 10 adds: real races on separate connections for every D26 scenario (A–I: whole-listing and 60 + 60 contention, concurrent orders, confirmation vs expiry, duplicate events, event vs cancellation, double cancellation, refund vs delivery, delivery failure vs resolution) with no-double-spend / conservation / orphan / duplicate-effect checks, the marketplace triggers, KYC / listing / payment / refund / delivery separation of duties, buyer and seller isolation, restricted KYC documents, and the absence of any fee, webhook, payout or mock provider. Phase 11 adds: real races on separate connections (recognition × delivery, two calculations claiming the same revenue, double settlement approval, double payout creation, double execution, bank-account change × execution, double reconciliation, refund × settlement), the finance triggers (append-only revenue / entitlements / transactions / reconciliations / allocation lines, frozen approved configuration and calculated figures, PAID payouts only to RECONCILED, claims never re-activated), separation of duties across the whole money chain, refusal of client-supplied amounts (no payout amount in any request schema), no bank credential in audit payloads (bank account id and last 4 only), DEMO write refusal, and organization isolation of every finance record. Phase 12A adds: the task allow-list (no arbitrary task, no import path from a payload), JSON-only Celery messages carrying job ids only (payload keys allow-listed; secrets / PII / files refused), the non-login SYSTEM actor (no role, no permission, refused at sign-in, hidden), environment isolation of jobs, Platform-Administrator-only job operations with audited cancel / requeue, sanitized job errors (no SQL text, no traceback to users), the append-only attempt and job-state triggers, and a Redis bound to localhost in compose (authentication + TLS required outside localhost). Phase 12B adds: object-storage and antivirus boundaries (`test_storage_av.py`, `test_storage_concurrency.py`), the Redis limiter with fail-open, trusted proxies, streamed body limits and production guards (`test_runtime_hardening.py`), and backup / restore safety (`test_operations.py`). The 29 Oct 2026 fixes (`test_fixes_29_identity.py`) cover the lockout not ending live sessions, rate-limit audit throttling, the request-id rule, the 500 envelope headers, DEMO isolation of user-less security rows and member-removal checks.
